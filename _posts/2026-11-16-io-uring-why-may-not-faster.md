把一个网络服务从 `epoll` 重构成 `io_uring`，系统调用次数确实可能下降，但 QPS 不一定上升， P99 延迟甚至可能变差。

这并不矛盾。

系统调用只是 I/O 路径中的一笔开销。数据拷贝、协议栈处理、任务调度、缓存局部性、业务计算和排队时间，都会进入最后的性能账单。`io_uring` 改变了应用与内核交换请求的方式，却不会让这些成本自动消失。

所以真正该问的不是“哪个接口更先进”，而是：当前服务的瓶颈在哪里，`io_uring` 省下的成本是不是那条关键路径上的主要成本。

## 一、就绪通知与完成通知：两种交互范式

先给一个直觉。

`epoll` 像后厨的出菜铃。 3 号桌的菜好了，铃声告诉服务员“可以来取了”，但服务员仍要跑一趟后厨，把菜端到桌上。

`io_uring` 更像一张共享订单表。应用把要做的事情写进订单表，内核执行后，再把结果写进完成表。应用不必先接收“可以做了”的通知，再单独发起同一个 I/O 操作。

换成术语，就是就绪通知与完成通知的差别。

### 1. `epoll`：先通知就绪，再显式读写

`epoll` 采用就绪通知（ Readiness-based ）机制。以一次网络接收为例，典型事件循环包含两步：

1.应用调用 `epoll_wait()`，等待一个或多个 Socket 变为可读；

2.应用取得就绪的文件描述符后，再调用 `read()` 或 `recv()` 搬运数据。

`epoll_wait()` 一次可以返回一批事件，因此等待成本能够被多个连接摊薄；但每个连接上的实际读写，仍要通过对应的 I/O 系统调用完成。使用边缘触发模式时，应用通常会持续读取，直到返回 `EAGAIN`。

这套模型的优势是成熟、直接。应用在知道 Socket 已经就绪后才准备缓冲区，也很容易让同一个事件循环线程持续负责固定的一组连接。

### 2. `io_uring`：先提交操作，再读取完成结果

`io_uring` 在用户态与内核态之间建立了两组共享内存结构：

•提交队列 SQ （ Submission Queue ）：应用准备 SQE ，描述要执行的操作、文件描述符和缓冲区；

•完成队列 CQ （ Completion Queue ）：操作完成后，内核写入 CQE ，记录结果和状态。

准备 SQE ，以及读取已经产生的 CQE ，都可以通过共享内存完成。不同线程是否共享同一个 ring 、由谁提交、由谁消费完成项，则取决于应用自己的并发模型；共享 ring 时仍要遵守相应的同步和内存顺序规则。

共享环减少的是提交请求和传递完成状态的协调成本。默认模式下，真正通知内核开始处理、或者等待尚未到来的完成事件，通常仍需要进入 `io_uring_enter()`。普通网络收发的数据也依然会经过协议栈并发生相应的数据拷贝，除非明确使用了零拷贝能力。

## 二、系统调用是怎样被摊薄的

`io_uring` 的优势并不只来自某一个“零系统调用”开关。批量提交、合并等待、多射操作和共享缓冲区共同决定了系统调用能够减少多少。

### 1. 默认模式：一次提交一批，同时等待完成

不开启 SQPOLL 时，应用填好 SQE 后，通常通过 `io_uring_enter()` 把请求提交给内核。一次调用可以提交多个 SQE ；设置 `IORING_ENTER_GETEVENTS` 后，还可以在同一次调用里等待至少指定数量的完成事件。

CQE 本身仍由应用从共享的 CQ 中读取并推进队列头。因此，这里的收益是把“提交一批请求”和“等待一批结果”合并到一次内核交互中，而不是让一个系统调用直接替应用处理所有完成项。

如果应用每轮都能积累一批请求，系统调用成本就会被多个 I/O 摊薄。如果工作负载始终是“提交一个、等一个”，批处理空间很小，收益自然也会缩小。

批量还会带来另一笔账：为了攒出更大的 batch ，应用可能让请求多等一会儿。吞吐优先的场景往往愿意接受这段等待，延迟敏感的场景则要控制批量大小和等待时间。

### 2. Multishot ：减少重复提交同类请求

普通 SQE 通常对应一个 CQE ，操作完成后，应用需要重新提交下一次请求。 Multishot 操作允许一个 SQE 连续产生多个 CQE ，从而减少重复提交和重新挂载监听的成本。

这类能力是逐步加入内核的： multishot poll 从 Linux 5.13 开始提供， multishot accept 从 5.19 开始提供， multishot recv 从 6.0 开始提供。

对网络服务而言， multishot accept 可以持续接收新连接， multishot recv 可以持续接收同一 Socket 上的数据。只要 CQE 中仍带有 `IORING_CQE_F_MORE`，应用就知道原来的请求还会继续产生完成事件。

接收操作还可以配合 provided buffers 。内核在数据到达时从应用准备好的缓冲池中选择一个缓冲区，并通过 CQE 告诉应用具体使用了哪一个。传统 provided buffers 从 Linux 5.7 开始提供，更高效的 ring-mapped provided buffers 从 5.19 开始提供。

这样做既减少了重复提交，也避免了为每个长期挂起的接收请求提前绑定一块独立缓冲区。

### 3. SQPOLL ：用轮询线程减少提交阶段的系统调用

创建 ring 时启用 `IORING_SETUP_SQPOLL`，内核会启动一个提交队列轮询线程。只要线程保持活跃，它就会主动检查 SQ ，应用发布新的 SQE 后不必每次调用 `io_uring_enter()` 通知内核。

这条路径能减少提交阶段的系统调用，但轮询本身需要 CPU 时间。高负载下，轮询线程可能持续运行；如果使用 `IORING_SETUP_SQ_AFF` 将它绑定到特定 CPU ，还需要为这个 CPU 做明确的容量规划。在 CPU 配额紧张的容器里，轮询线程也会与业务线程争夺调度时间。

空闲时间超过 `sq_thread_idle` 后，轮询线程会睡眠，并设置 `IORING_SQ_NEED_WAKEUP`。应用下一次提交时需要通过 `io_uring_enter()` 唤醒它， liburing 通常会自动处理这个判断。线程恢复后，后续提交仍可继续走轮询路径。

因此， SQPOLL 更适合提交足够密集、 CPU 预算明确的负载。请求稀疏时，普通批量提交往往更省资源。

## 三、系统调用之外，还有三笔更大的账

减少系统调用并不等于缩短全部 I/O 路径。网络事件循环、文件系统执行方式和资源注册策略，都可能改变最终结果。

### 1. 网络 I/O ：事件循环是否真正围绕完成模型重构

成熟的 `epoll` 服务通常已经形成稳定的 Reactor 模型：一个事件循环线程负责固定的一组连接，完成收包、解析、业务处理和发送。配合 `SO_REUSEPORT`、 CPU 亲和性和合理的中断配置，这种模型能够保持较好的缓存局部性。

如果迁移时只是把 `epoll_wait()` 换成 `io_uring` 的 poll 操作，而收发、缓冲区和事件循环仍按原来的方式组织，那么应用只使用了新接口的一小部分能力。系统调用可能少了一些，额外的状态管理和调度路径却未必减少。

面向完成模型重新组织网络路径时，通常会组合使用批量提交、 multishot accept/recv 、 provided buffers ，以及适合发送路径的 `IORING_OP_SEND_ZC`。其中零拷贝发送在条件不满足时可能回退到复制路径，应用需要根据通知 CQE 判断缓冲区何时可以安全复用。

任务完成的处理时机同样会影响延迟和缓存局部性。`IORING_SETUP_COOP_TASKRUN` 可以减少为及时处理 task work 而产生的强制中断和跨核 IPI ；`IORING_SETUP_SINGLE_ISSUER` 让应用声明只有一个提交者，从而帮助内核简化内部同步。它们是事件循环设计的一部分，不是打开后就必然变快的通用开关。

Linux 6.9 起提供的 `IORING_REGISTER_NAPI` 可以为 ring 配置 NAPI busy poll ，其作用与网络 busy polling 一致：用更多 CPU 轮询时间换取更短的收包等待。是否有效取决于网卡、驱动、队列亲和性和负载，配置不当也可能增加 CPU 占用。

网络路径最终快不快，要同时看批量大小、每条连接的活跃度、软中断与应用线程的 CPU 分布、 NUMA 位置，以及业务逻辑本身占用了多少时间。

### 2. 文件 I/O ：能否异步执行取决于具体路径

普通磁盘文件并不适合用 `epoll` 监听。`epoll_ctl()` 通常无法把普通文件加入监听集合；而 `poll()`、`select()` 看到的普通文件又通常始终处于就绪状态，不能据此判断下一次访问是否会等待磁盘。

`io_uring` 为文件 I/O 提供了统一的提交与完成接口，但每个请求在内核中的执行方式并不相同。

内核会尽量先走不会阻塞的路径。 Buffered Read 命中 Page Cache 时，数据可能直接复制到用户缓冲区并很快完成；未命中时，文件系统和块设备可能异步发起读取。遇到不能在当前上下文安全完成、又缺少合适异步路径的操作，内核可以把工作转交给 `io-wq`。

`io-wq` 中的 worker 分为有界和无界两类，并受 worker 上限和进程资源限制约束，应用也可以调整最大数量。它避免了提交线程被阻塞，但线程调度、上下文切换和并发放大仍然会产生开销。实际是否进入 `io-wq`，取决于操作类型、文件系统、缓存状态、内核版本和使用的标志，不能只靠“Buffered”或“Direct”两个标签判断。

对 NVMe 上的大量 Direct I/O ，`io_uring` 更容易发挥深队列、批量提交和原生异步完成的优势。对大量命中 Page Cache 的小读取，内存拷贝和应用处理反而可能占据更大比例，接口本身的差距会缩小。

### 3. 注册资源：降低逐次开销，也承担长期成本

一次 I/O 不只包含设备读写。内核还要校验用户缓冲区、取得文件对象引用，并为异步操作维护这些资源的生命周期。 Direct I/O 等需要设备直接访问用户内存的路径，还涉及用户页的固定和映射。

`io_uring` 可以把一部分逐次开销提前支付：

1.**Fixed Buffers**：通过 `IORING_REGISTER_BUFFERS` 预先注册缓冲区。内核长期固定并映射这些页面，后续使用 fixed read/write 时不必为每个 I/O 重复建立映射；

2.**Fixed Files**：通过 `IORING_REGISTER_FILES` 预先注册文件描述符，后续使用表内索引，减少逐次获取和释放文件对象引用的开销。

Fixed Buffers 本身并不等于零拷贝。它优化的是缓冲区校验、固定和映射等准备工作；数据是否复制，仍由具体 I/O 操作和内核路径决定。

注册资源也不是免费的。固定页面长期占用内存，缓冲池需要处理容量、复用和生命周期，固定文件表也要维护更新。 I/O 越小、频率越高、缓冲区复用越稳定，这些优化越容易摊回注册成本。

## 四、应该怎样选择？

`epoll` 和 `io_uring` 并不是同一条刻度上的新旧版本。一个是成熟的就绪通知接口，一个是覆盖网络、文件、定时器等操作的异步提交与完成框架。

### 继续使用 `epoll`

下面这些场景中，迁移通常不会自动产生足够大的收益：

•服务以网络 I/O 为主，现有 Reactor 模型成熟稳定；

•CPU 主要消耗在业务逻辑、序列化、加密或数据拷贝，而不是系统调用；

•请求难以形成有效批量，或者业务对排队延迟极其敏感；

•运行环境的内核版本、可用 CPU 或内存预算无法支持计划使用的特性；

•当前没有剖析数据证明 `epoll_wait()`、`read()`、`write()` 已经成为主要瓶颈。

在这些条件下，继续优化事件循环、绑核、缓冲区和业务路径，往往比更换 I/O 接口更直接。

### 评估 `io_uring`

下面这些负载更值得投入迁移和压测成本：

•存储引擎需要维持较深的 NVMe I/O 队列，并频繁进行 Direct I/O ；

•网络服务拥有大量活跃连接，能够利用批量提交、 multishot 和 provided buffers 重构完整事件循环；

•系统同时处理网络、文件和定时器，希望在一套完成模型中统一调度；

•性能剖析已经显示系统调用、重复提交、资源查找或缓冲区映射占据可观 CPU ；

•团队能够固定内核与 liburing 版本，并愿意针对亲和性、队列深度和缓冲池做持续调优。

PostgreSQL 18 的 AIO 子系统就提供了一个很好的边界示例：它可以选择 `worker`、`io_uring` 或同步方式执行符合条件的异步 I/O ，默认仍是 `worker`。接口只是执行策略之一，真正的收益来自上层扫描、预读和并发调度与底层能力的配合。

如果现有 `libaio` 与 O_DIRECT 路径已经稳定，功能也足够，迁移同样需要用数据证明价值。统一接口和更丰富的操作类型是长期收益，但不会自动抵消重构、调试和版本兼容成本。

## 五、压测时该看什么

比较 `epoll` 与 `io_uring`，至少要固定并记录这些条件：

•内核、 liburing 、网卡驱动和文件系统版本；

•请求大小、连接活跃度、读写比例和突发分布；

•ring 大小、队列深度、每批提交数量和等待策略；

•是否启用 SQPOLL 、 multishot 、 provided buffers 、 Fixed Files 、 Fixed Buffers 或零拷贝发送；

•应用线程、 SQPOLL 、软中断和存储队列的 CPU/NUMA 亲和性；

•吞吐、平均延迟、 P99/P999 、 CPU 时间、系统调用次数、上下文切换和缓存未命中。

还要比较完整应用，而不是只测空事件循环。系统调用在微基准中可能占比很高，一旦加入协议解析、业务逻辑和数据复制，它在总耗时中的比例可能迅速下降。

## 结论

`io_uring` 的核心价值，是用共享环、批量操作和统一完成模型降低 I/O 的协调成本，并为网络与存储提供一组可以组合的异步能力。

它不一定比 `epoll` 快，原因也很具体：

1.默认模式仍可能需要系统调用，收益取决于批量能做多大；

2.SQPOLL 、 busy poll 等机制会用 CPU 时间换取更少的唤醒和更低的延迟；

3.网络服务需要围绕完成模型重构事件循环，简单替换通知接口只能获得有限收益；

4.文件请求可能走原生异步路径，也可能借助 `io-wq`，实际成本取决于操作和运行环境；

5.Fixed Buffers 、 Fixed Files 和零拷贝能力都有明确的适用条件与资源代价。

决定迁移之前，先用性能剖析确认瓶颈，再按真实负载做端到端压测。系统调用少了，只能说明一项成本下降了；只有吞吐、尾延迟和资源占用一起改善，迁移才真正完成了它的任务。
